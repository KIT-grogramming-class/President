設計ドキュメント（チーム内で共有）の方針に従い、**実験駆動で複数の戦略を比較しながら段階的に強化** した。

## 2. コミット履歴と意図

### Commit 1: `build: Mac対応のビルド設定とビルド成果物の除外`

開発環境を整えるための前提コミット。

- 提供された `libplayingcards.a` は Linux 用バイナリで、開発環境の macOS（arm64）では直接リンクできない
- mac 用に提供されている `thinkTA1-for-mac-arm64.o` を直接リンクする方法に切り替え
- Makefile に **プラットフォーム判定ロジック** を追加し、`make` 一発で正しい `thinkTA1.o` がコピーされるようにした
- 元の Makefile にあった `cardset.cpp`（拡張子の typo）を `cardset.o` に修正
- `.gitignore` を新設し、`*.o` などのビルド成果物がリポジトリに混入しないようにした

これにより班員のうち Linux/Mac どちらでも `make` だけでビルドが通る。

### Commit 2: `feat: Group1 プレイヤークラスを実装（v2.5: 評価関数派）`

AI の本体。`Player` クラスを継承した `Group1` を新規作成。

#### 設計の三層構造

設計ドキュメントの方針通り、以下の三層で構成：

1. **信念追跡層**: `approve()` で既出カードを `played` に記録
2. **手列挙層**: 合法手（同ランク組＋ジョーカー併用）を全パターン生成
3. **評価層**: 各手を点数化し、最高得点を選択

#### 評価関数の構成要素

```
score = 3.0 × (通る確率)               # 解析的 or MC
      + 1.2 × (15 - カード強度)        # 弱いカードを使うほど得
      − jokerPenalty(手札数)           # 手札数で動的に変化
      − pairPenalty(手札数) × 崩した枚数 # 同上
      + 4.0 × pass × (ライバルリーチ判定)
      + 終盤ボーナス(手札数)
      + リーダー時補正
      + 上がり/上がり前ボーナス
```

#### 重み調整の経緯（試行錯誤の記録）

最初の評価関数 v2 では `pass × 10` の重みを使ったが、実験すると **強いカードで「確実に通す」を選びがち** で、v1 より弱くなった（25.5% → 21.4%）。

そこで `pass × 3` まで弱め、代わりに `(15 - 強度) × 1.2` を強めたところ、一気に **TA1 に並ぶ強さに到達**（22% → 32%）。「**通る確率は飾りで、いかに弱いカードを早く手放すかが本質**」という大富豪の本質を実装で確認できた。

これは設計ドキュメントの「実験で決める」方針が功を奏した瞬間で、レポートの考察ポイントとして記録する価値がある。

### Commit 3: `feat: daifugou.cpp で Group1 をプレイヤーとして登録`

`registerPlayers()` に `Group1` を追加して大会形式で動かせるようにした。

## 3. 実験（採用しなかった候補も含む）

設計ドキュメントの「3候補比較実験」を実施。結果のサマリー：

### 候補A: 評価関数派（採用）

通る確率や強度を重み付けした線形評価関数。
解釈可能で軽量、**最終的にこれが最強だった**。

### 候補B: モンテカルロ派（部分実装、不採用）

`approve()` で得た既出カード情報から相手の手札をランダムにサンプリングし、「自分の手が返される確率」を実測した。

**結果**: 解析的計算と差がなかった（約28% vs 30%）。

考察:
- 解析的な「強いランクで揃うか」のヒューリスティクスがすでに本質を捉えていた
- サンプル数 K=20 では分散が大きく、ノイズが信号を上回った可能性
- プレイアウト方策がランダムすぎて、実際の TA1 など強い相手の挙動を反映しない

これは「**シンプルな解法が複雑な解法と同等以上**」という古典的な工学の教訓そのもの。レポートでは **不採用にした理由** として記述する価値あり。

### 候補C: ハイブリッド派（時間切れで未実装）

A の評価関数を B の中で使う構成。理論上は最強だが、A 単独で TA1 越えできたため、**実装コストが見合わないと判断**して保留。

## 5. 主な学び（レポート用考察ポイント）

### A. ドメイン知識を素直に重みにすると効く

「弱カードを早く手放す」「ジョーカーは温存」「ペアは崩さない」など、**人間が経験的に知っているコツをそのまま線形項で表現**したら、深い探索なしで TA1 越えに到達できた。設計ドキュメントで議論した「**特徴量＋手書き重み = 機械学習なしで十分**」が実証された。

### B. シンプルな解法 > 複雑な解法（今回の場合）

MC pass 確率は理論的により正確だが、**実測では効果が出なかった**。理由は：

- 解析的ヒューリスティクスが本質を捉えていた
- MC のサンプル数が少なくノイズが大きい
- プレイアウト方策が単純で実際の対戦相手を反映しない

「より高度な手法を試す前に、シンプルな手法を尽くせ」という工学の原則を確認。

### C. 動的な重みが効果的

手札数によって重みを変える（ジョーカー温存・ペア温存の動的化）ことで、序盤と終盤で異なる戦略を実現。**静的な評価関数より動的なものが強い**という直感的な結果が出た。

### D. 実験駆動で進めることの価値

- v2 では `pass × 10` で弱くなり、`pass × 3` で強くなった
- 1000試合の対戦結果を見ながら weight を調整 → 数日で実用レベル
- 「机上の理論で最強アルゴリズムを設計してから実装」より **「動かしながら測って改良」** が効率的

これは演習自体のメッセージ（**実験で意思決定する**）と整合した。

## 6. 次のステップ（v3 系として継続予定）

現状の v2.5 は ThinkTA1 と統計誤差ギリギリで上回っている状態（10000試合で +0.28%）。さらに上を狙うため、以下を順次試す：

1. **終盤ルックアヘッド** — 手札 ≤4 の局面で深読みする
2. **MCプレイアウト** — 相手手札サンプリング＋ゲーム終局までシミュレート
3. **重み自動チューニング** — Python で grid search / CMA-ES により最適化

これらは「シンプルな解法の限界が見えてきた段階で、より複雑な手法を試す」という段階に対応する。

各実装の効果は対戦実験で検証し、効いたものだけを残す方針。
